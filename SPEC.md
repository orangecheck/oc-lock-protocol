# OC Lock Protocol v2.4 — Specification

**Status:** Stable
**Version:** 2.4.0 (2026-10-24). 2.0.0 was published 2026-04.
**Supersedes:** LOCK Protocol v1.0 (adaptor signature) and v1.1 (Proof-of-Access)

---

## 0. Notation

- All bytes serialized as lowercase hex unless marked `base64url`.
- `||` denotes byte concatenation.
- `KDF()` = HKDF-SHA256 per RFC 5869.
- `AEAD()` = AES-256-GCM per NIST SP 800-38D (12-byte IV, 16-byte tag).
- `ECDH(k, P)` = standard X25519 function per RFC 7748. Output is 32 bytes.
- `BIP322(addr, msg)` = BIP-322 signature of `msg` by `addr`, encoded as base64.
- Canonical JSON = UTF-8 encoded JSON with lexicographically sorted object keys, no insignificant whitespace, LF-terminated. See §7.

## 1. Actors

- **Sender** — the party creating a vault.
- **Recipient** — the party able to unseal the vault.
- **Device** — a browser or app instance holding a device keypair bound to a Bitcoin identity.
- **Directory** — a Nostr relay (or set of relays) that stores device-key records.
- **Relay (optional)** — a server that holds payment-gated content keys and releases them upon observing a qualifying Bitcoin payment.

A sender and recipient may be the same person (vault-for-self, password manager pattern).

## 2. Identities

An **OC identity** is the pair `(btc_address, attestation_id)` where:

- `btc_address` is a mainnet Bitcoin address (P2WPKH, P2TR, or P2PKH)
- `attestation_id` is the SHA-256 of a canonical OrangeCheck message signed by that address per the [OrangeCheck SPEC §3](https://ochk.io/docs/spec)

A recipient MUST have an OC identity known to the sender. OC Lock does not publish recipient pubkeys; it publishes **device keys** (§3) addressable by the recipient's Bitcoin address.

## 3. Device keys

A **device key** is a long-lived X25519 keypair generated by a recipient in a particular client/device and bound to their Bitcoin identity by a BIP-322 signature.

### 3.1 Generation

```
(device_sk, device_pk) := x25519_keygen()      // 32-byte each
```

`device_sk` MUST be stored in a confidential local store (IndexedDB with `extractable=false` via WebCrypto if available, else plaintext). `device_sk` MUST NOT leave the device.

### 3.2 Binding

The recipient signs the **binding statement** with their Bitcoin address:

```
binding_statement := "oc-lock:device-bind:v2\n"
                  || "address: "        || btc_address    || "\n"
                  || "device_pk: "      || hex(device_pk) || "\n"
                  || "device_id: "      || device_id      || "\n"    // random 16-byte hex
                  || "created_at: "     || iso8601_utc    || "\n"
```

`binding_sig := BIP322(btc_address, binding_statement)`.

**v3 statement (publishers MUST emit).** A v3 statement additionally commits to the device's Nostr pubkey (§3.4), so the record authorizes exactly one Nostr key:

```
binding_statement := "oc-lock:device-bind:v3\n"
                  || "address: "        || btc_address    || "\n"
                  || "device_pk: "      || hex(device_pk) || "\n"
                  || "nostr_pk: "       || hex(nostr_pk)  || "\n"    // x-only, lowercase
                  || "device_id: "      || device_id      || "\n"
                  || "created_at: "     || iso8601_utc    || "\n"
```

A verifier MUST reject a v3 record whose `event.pubkey` differs from the signed `nostr_pk`. Readers MUST continue to accept v2 records for sealing to `device_pk` (§4.2).

### 3.3 Publication

The **device record** is published to Nostr as an addressable event of kind `30078`:

```
event.kind    = 30078
event.tags    = [
  ["d",           "oc-lock:device:" || btc_address],
  ["addr",        btc_address],
  ["device_id",   device_id],
  ["device_pk",   hex(device_pk)],
  ["alg",         "x25519"],
  ["binding_sig", base64(binding_sig)]
]
event.content = binding_statement   // exact bytes, including LFs
event.pubkey  = ephemeral_nostr_pubkey   // see §3.4
event.created_at = unix_seconds
```

A record is evidence only for the address in its signed `binding_statement`. A reader MUST reject a bind whose `d` tag is neither `"oc-lock:device:" || address` nor the §3.6 per-device form for that signed address, or whose `addr`, `device_id` or `device_pk` tag differs from its signed statement, and a reader resolving address `A` MUST discard every record whose signed address is not `A`. The `d` tag is writable by any publisher, so a record returned by a `#d` query for `A` may carry a valid binding for a different address. A revocation is read from its signed statement alone (§3.5).

Clients SHOULD publish to at least three relays from a diverse set. The reference app uses `relay.ochk.io`, `nos.lol`, `relay.primal.net`, `relay.damus.io` and `nostr.oxtr.dev`, the default set in `@orangecheck/nostr-core`.

### 3.4 Nostr authorship

The Nostr event `pubkey` is not tied to the user's Bitcoin identity — any ephemeral Nostr key works, because the authenticity proof is the BIP-322 `binding_sig` verifiable against `btc_address`. A fresh ephemeral Nostr keypair SHOULD be derived deterministically from the device:

```
nostr_sk := hkdf(ikm=device_sk, salt="oc-lock/v2/nostr-key", info="nostr-sk", L=32)
```

This avoids asking wallets to hold Nostr keys.

**Authorizing a Nostr pubkey.** Protocols that treat a device record's `event.pubkey` as an identity-bound signing key (OC Chat inbox keys, device signatures) MUST derive that authorization from the signed statement, not from the event author:

- A v3 record authorizes its signed `nostr_pk`.
- A v2 statement does not name a Nostr key, so its `event.pubkey` is the event author's assertion. From **2027-01-21T00:00:00Z** by the verifier's clock, a v2 record authorizes no Nostr key. Before that instant, a v2 record authorizes its `event.pubkey` only while no v3 record exists for the same `(btc_address, device_id)` and that pair appears under exactly one `event.pubkey` in the records the verifier holds; when it appears under more than one, none of them is authorized.

A v2 bind remains live for sealing to its `device_pk` (§3.2, §3.5): a sender still encrypts to the device. A device whose live binds are all v2 has no authorized inbox key, so it receives envelopes by link or another channel the sender chooses, not at a Nostr inbox.

**Re-binding a v2 device.** A client that holds the `device_sk` of a live v2 bind SHOULD publish a v3 statement for the same `btc_address`, `device_id`, `device_pk` and `created_at`, naming the `nostr_pk` derived from `device_sk` (above), as a record under that key with the §3.3 `d` tag. The re-bind MUST carry the v2 statement's `created_at`. A revocation of the device then retires the v3 bind as it retires the v2 bind (§3.5); a later `created_at` would leave the v3 bind live past a revocation dated between the two, including one the re-binding client has not seen. Published under the same key and `d` tag, the v3 record takes the v2 record's place at every relay that holds both (NIP-33). Only the device can re-bind itself, because the statement names a key derived from its secret; the wallet signs the statement. A client SHOULD offer the re-bind for each of its own devices whose live binds are all v2, and SHOULD say when v2 stops naming an inbox.

### 3.5 Rotation and revocation

A device stops receiving new envelopes only through a **revocation**: a kind-30078 event whose `content` is the revocation statement, signed by the address.

```
revocation_statement := "oc-lock:device-revoke:v2\n"
                     || "address: "        || btc_address    || "\n"
                     || "device_id: "      || device_id      || "\n"
                     || "revoked_at: "     || iso8601_utc    || "\n"
```

`binding_sig := BIP322(btc_address, revocation_statement)`. The event carries the §3.3 tags with `["device_pk", "revoked"]` and MUST use the §3.3 `d` tag, `"oc-lock:device:" || btc_address`, which every reader queries. A device revoking itself SHOULD carry the revocation under its own Nostr key, so that every relay that accepts it stops serving that device's bind, and MAY use a fresh key. A revocation of another device SHOULD be carried by a fresh Nostr key. A key that carries another live bind of the address MUST NOT carry a revocation: relays replace a record by `(pubkey, kind, d)` (NIP-33), so the revocation takes that bind's place. The authority is the address's signature, so a lost device can be revoked with the wallet alone. A revocation statement names no Nostr key, and a reader MUST NOT reject one for its `event.pubkey`. Nor for its tags: a reader takes a revocation's address and `device_id` from its signed statement, and MUST NOT reject one whose `binding_sig` verifies for that address because its `addr`, `device_id` or `device_pk` tag is missing or says something else, or because it is filed under another `d` tag. A publisher still writes the tags above; a reader that refused a revocation over them would leave the device live (vector `r03`).

**Which binds are live.** A reader resolving address `A` collects the device records it received for `A` from every relay it queried, and discards each one whose `binding_sig` does not verify (§3.3). Then, for each `device_id` `D`:

1. Let `R` be the latest signed `revoked_at` among the remaining revocations of `(A, D)`.
2. A bind of `(A, D)` is **live** if there is no such revocation, or if its signed `created_at` is later than `R`. A bind whose `created_at` equals `R` is retired.
3. This holds whichever Nostr key carried each record, whichever `d` form (§3.3, §3.6) filed it, and whichever relay served it. A revocation that one relay holds retires the bind that another relay still serves.
4. A bind whose signed `created_at` is later than the reader's clock plus a skew allowance (10 minutes RECOMMENDED) is **not live yet**. It becomes live when the clock reaches it, unless a revocation retires it first. A reader SHOULD still list it, so that it can be revoked.

The times are the signed `created_at` and `revoked_at`, compared as instants. `event.created_at` is set by whoever publishes the event and orders nothing here. A revocation statement signs no `created_at`. One that verifies but has no `revoked_at` line, or one that does not read as an instant, bounds nothing: it retires every bind of its `(A, D)`, whatever that bind's `created_at`, a later one included (vector `r03`). `event.created_at` does not stand in for the missing time, since anyone who republishes the event can set it. A revoker MUST sign a `revoked_at` (below); the remedy for an undated revocation is a new `device_id`, as for one dated in the future (LIFECYCLE §1.1). A revocation whose `binding_sig` is empty or does not verify for `A` retires nothing. Published under the device's own Nostr key, it still replaces that key's earlier record at the relays that take it (NIP-33). That is relay behavior: every other relay keeps serving the bind.

Conforming senders MUST seal only to live binds. When no bind for `A` is live, the sender MUST NOT seal, and reports `E_REVOKED`.

**Dating a revocation.** A revoker MUST sign a `revoked_at` no earlier than its own clock, and no earlier than the latest signed `created_at` among the binds of `(A, D)` it holds. A revocation dated so retires every bind of the device the revoker has seen, including one dated ahead. A client that publishes a revocation SHOULD read the device's records again before it reports the device as revoked.

To **rotate**, a recipient binds a new device (§3.1–§3.3, with a new `device_id`) and revokes the old `device_id`. Publishing the new record does not retire the old one. Each device publishes under its own Nostr key (§3.4), so the two records sit at different NIP-33 coordinates and no relay replaces one with the other.

### 3.6 Multi-device

A recipient with multiple devices publishes one record per device. Each device publishes under its own Nostr key (§3.4), so the devices' records share the §3.3 `d` tag and stay apart by `pubkey`. New records SHOULD use the §3.3 form. The per-device form `oc-lock:device:<addr>:<device_id>` remains valid and a reader accepts a record under it (§3.3), but a `#d` query for the address does not return it. Senders MUST encrypt once per live device (§3.5, §4.2, `recipients[]`).

## 4. Envelope format

A sealed vault is a single canonical JSON object called the **envelope**. It is referred to by file extension `.lock` and MIME type `application/vnd.oc-lock+json`.

### 4.1 Envelope schema

```json
{
  "v": 2,
  "kind": "identity" | "payment",
  "id": "<32-byte hex envelope id, SHA-256 of canonical envelope without this field and without sig>",
  "alg": { "kem": "x25519", "aead": "aes-256-gcm", "kdf": "hkdf-sha256" },
  "from": {
    "address": "<btc address of sender>",
    "attestation_id": "<sha256 of sender's OC canonical message, optional>"
  },
  "recipients": [
    {
      "address": "<btc address of recipient>",
      "device_id": "<recipient device id>",
      "device_pk": "<32-byte hex X25519 pubkey>",
      "eph_pk": "<32-byte hex X25519 ephemeral pubkey produced for this recipient>",
      "wrapped_key": "<base64url(aead(content_key, kek, nonce_kek))>",
      "nonce_kek": "<12-byte hex>"
    }
  ],
  "ciphertext": "<base64url(aead(payload, content_key, nonce_ct))>",
  "nonce_ct":   "<12-byte hex>",
  "hint":       "<optional plaintext hint, UTF-8, <= 200 bytes, leaking only what sender chooses>",
  "created_at": "<iso8601 utc>",
  "expires_at": "<iso8601 utc | null>",
  "payment": null | {
    "amount_sats": <positive integer>,
    "address":     "<btc address that must be paid>",
    "confirmations": <non-negative integer, default 1>,
    "relay":       "<https url of OC Lock relay>"
  },
  "sig": {
    "alg":     "bip322",
    "pubkey":  "<sender btc address>",
    "value":   "<base64(BIP322(sender_addr, id))>"
  }
}
```

### 4.2 Encryption procedure (identity mode)

Given a `payload` (bytes) and one or more recipient device records:

1. Generate random `content_key` (32 bytes).
2. Generate random `nonce_ct` (12 bytes).
3. Compute `ciphertext = AES-256-GCM(content_key, nonce_ct, payload, aad=envelope_id_draft)` where `envelope_id_draft` is the SHA-256 of the canonical envelope up to and excluding `ciphertext`, `sig`, and `recipients[*].wrapped_key` fields.
4. For each recipient device:
   a. Generate an ephemeral X25519 keypair `(eph_sk, eph_pk)`.
   b. `shared = X25519(eph_sk, device_pk)` (32 bytes).
   c. `kek = HKDF-SHA256(ikm=shared, salt=nonce_ct, info="oc-lock/v2/kek:" || device_id, L=32)`.
   d. Generate `nonce_kek` (12 bytes).
   e. `wrapped_key = AES-256-GCM(kek, nonce_kek, content_key, aad=device_id)`.
   f. Zeroize `eph_sk`.
5. Compute final canonical envelope; set `id = sha256(canonical_bytes_without_sig)`.
6. `sig.value = BIP322(sender_addr, id)`.
7. Zeroize `content_key`.

### 4.3 Decryption procedure (identity mode)

Given an envelope and a local `(device_id, device_sk)` pair:

1. Recompute `id` from the envelope and compare to `envelope.id`. Reject on mismatch.
2. Reject unless `sig.pubkey` equals `from.address`. Verify `sig.value` against `id` using BIP-322 and `sig.pubkey`. Reject on failure. (Clients MAY skip sender verification for sender == self.) A client that skips verification, or opens an envelope whose `sig.value` is empty, MUST NOT present `from.address` as the authenticated sender, and MUST NOT treat `from.address` equal to its own address as proof that it sent the envelope.
3. Find a recipient entry matching your local `device_id`. If none, this vault is not for you — reject.
4. `shared = X25519(device_sk, eph_pk)`.
5. `kek = HKDF-SHA256(ikm=shared, salt=nonce_ct, info="oc-lock/v2/kek:" || device_id, L=32)`.
6. `content_key = AES-256-GCM.decrypt(kek, nonce_kek, wrapped_key, aad=device_id)`. Reject on tag failure.
7. `payload = AES-256-GCM.decrypt(content_key, nonce_ct, ciphertext, aad=envelope_id_draft)`. Reject on tag failure.
8. Zeroize `shared`, `kek`, `content_key`.

### 4.4 Payment mode

Payment mode replaces step 4 in §4.2 with a single "recipient" that is the **relay**:

```json
"recipients": [
  {
    "address": "<relay identity>",
    "device_id": "oc-lock-relay",
    "device_pk": "<relay X25519 pubkey>",
    "eph_pk": "...",
    "wrapped_key": "...",
    "nonce_kek": "..."
  }
],
"payment": {
  "amount_sats": 10000,
  "address":     "bc1q...",
  "confirmations": 1,
  "relay":       "https://oc-lock.example/relay"
}
```

The relay holds the content key wrapped for its own device key. A recipient unsealing a payment-mode vault performs:

1. Authenticate to the relay using OC sign-in (OrangeCheck challenge-response over the recipient's Bitcoin address).
2. Request release: `POST /release { envelope_id, unlock_address, tx_proof }` where `tx_proof` identifies a confirmed Bitcoin transaction paying `payment.amount_sats` to `payment.address` with at least `payment.confirmations` confirmations.
3. Relay verifies via a Bitcoin block explorer that the tx exists, has the required amount and confirmations, and is spent from `unlock_address` (if vault requires address binding).
4. Relay unwraps `content_key` using its own `device_sk`, re-wraps it for the recipient's **authenticated** device (fetched from Nostr), and returns the new `recipients[]` entry.
5. Recipient decrypts normally via §4.3.

The relay is a trust anchor. Clients MUST display the relay URL and identity prominently before accepting payment-mode vaults. Anyone may run a relay; the reference implementation is permissionless and stateless between a funded release request and its response.

### 4.5 Chat and re-wrap mode (OC Chat)

[OC Chat](https://github.com/orangecheck/oc-chat-protocol) is a **mode of OC Lock** that operates the envelope continuously over a thread. It adds two `kind` values — `"chat"` and `"chat-seal"` — and one normative change to id/AAD computation for those kinds.

**Recipient-exclusion rule (NORMATIVE).** For `kind ∈ {"chat", "chat-seal"}`, the `recipients[]` array is delivery routing, not content, and is excluded from both the AEAD AAD and the signed envelope id:

- `envelope_id_draft` (the AAD, §4.2 step 3) is computed with `ciphertext=""`, `sig={}`, **and `recipients=[]`** (the entire array emptied, not merely each `wrapped_key`).
- the envelope `id` (§4.1) is computed with `sig.value=""` **and `recipients=[]`**.

This makes a chat envelope **re-keyable**: a holder — a payment relay (§4.4) or an OC Chat seal beacon (§4.6) — MAY replace `recipients[]` after sealing (a **re-wrap**), and the `id`, the sender `sig`, and the ciphertext GCM tag all remain valid. The re-wrap output is a detached `recipients[]` entry merged locally **without** recomputing the signed id. For `kind ∈ {"identity","payment"}` the base rules of §4.2 are unchanged. A `"chat"` envelope MAY carry an optional `postage` object (Lightning anti-spam); thread state (`conversation_id`, `seq`, `parent_id`) lives inside the encrypted payload. See `oc-chat-protocol` SPEC §3, §5, §6.

### 4.6 Seal mode (OC Chat block-height timelock)

A `"chat-seal"` envelope carries a `seal` object parallel to `payment`:

```json
"seal": { "unlock_block": <int>, "anchor": "beacon" | "cltv",
          "beacon_id": "...", "beacon_url": "...", "redundant_beacon": null | { },
          "confirmations": <int>, "cltv_outpoint": "<optional>" }
```

The sender wraps `content_key` to a **named beacon** device; the beacon releases it (re-wrap, §4.5) only after the Bitcoin chain reaches `unlock_block + confirmations`. For `anchor="beacon"` this is **beacon-enforced policy, not Bitcoin consensus** — a colluding beacon threshold can release early, and beacon disappearance permanently bricks the seal. Implementations MUST NOT describe a v0 beacon seal as "trustless". `anchor="cltv"` (reserved) is the consensus-enforced upgrade path — spending a `CHECKLOCKTIMEVERIFY`-encumbered output reveals the key in its witness — structurally pre-wired via `cltv_outpoint` and not shipped in v0. Full detail and the honest trust posture: `oc-chat-protocol` SPEC §7 + SECURITY.md.

## 5. Canonicalization

The canonical byte representation of an envelope is required for computing `id` and for BIP-322 signing. Canonical form:

- UTF-8 JSON with keys sorted lexicographically at every level.
- No insignificant whitespace (no spaces after `:` or `,`, no leading/trailing whitespace).
- Arrays preserve order. Within `recipients[]`, entries MUST be sorted by `device_id` ascending.
- Numbers serialized with no fractional zeros and no exponents for integers within IEEE 754 double range.
- Strings serialized with `\uXXXX` escapes only for control characters and `"` / `\`; all other codepoints literal.
- Final byte is LF (`0x0a`).

Reference: [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785), with the additional requirement on `recipients[]` ordering.

`envelope_id_draft` used as AAD in step 4.2.3 and 4.3.7 is computed from the envelope with `ciphertext=""`, `sig={}`, and each `recipients[*].wrapped_key=""`, then canonicalized.

## 6. Errors

Client errors MUST use these codes. Users see short human-readable messages; logs see the code.

| Code | Meaning |
|---|---|
| `E_NO_DEVICE` | No device key found for this browser. Recipient must register. |
| `E_NOT_ADDRESSED` | Envelope does not include the recipient's `device_id`. |
| `E_BAD_SIG` | Sender BIP-322 signature did not verify. |
| `E_BAD_TAG` | AEAD authentication failed (tampered envelope or wrong key). |
| `E_EXPIRED` | `expires_at` is in the past. |
| `E_REVOKED` | No device record for the recipient's address is live: a verified revocation retired each one (§3.5). |
| `E_PAYMENT_UNMET` | Relay could not verify required payment. |
| `E_RELAY_UNREACHABLE` | Relay did not respond. |
| `E_BLOCK_UNMET` | (OC Chat) Seal release requested before `unlock_block + confirmations`. |
| `E_BEACON_UNAVAILABLE` | (OC Chat) Seal beacon did not respond. |
| `E_NO_POSTAGE` | (OC Chat) `pay-to-reach` message from a non-contact lacked valid postage. |
| `E_BAD_POSTAGE` | (OC Chat) `SHA-256(preimage) != payment_hash`, or the recipient/amount/nonce binding failed. |
| `E_THREAD_GAP` | (OC Chat) `parent_id` does not resolve to a held parent envelope id. |

## 7. Security model

### 7.1 What OC Lock proves

- **Authenticity**: The envelope was signed by the holder of `from.address` at a specific moment (BIP-322 over `id`).
- **Confidentiality**: Only holders of a `device_sk` listed in `recipients[]` can derive `content_key`.
- **Identity binding**: A recipient's `device_pk` is bound to their `btc_address` by a BIP-322 signature in the Nostr directory record. Senders MUST verify the binding before encrypting.

### 7.2 What OC Lock does NOT prove

- **Order / freshness**: Envelopes include `created_at` but are not ordered. Use OrangeCheck challenge-response for freshness-critical flows.
- **Delivery**: The protocol does not ship vaults. Use any transport (URL, email, Nostr, dead drop).
- **Metadata privacy**: `from.address`, `recipients[*].address`, `hint`, and `payment.address` are plaintext. A sender who wants metadata privacy MUST redact these and rely on out-of-band addressing.

### 7.3 Trust assumptions

- **Identity mode**: No trust in any third party. Nostr relays may censor but cannot forge: the BIP-322 binding signature is verifiable offline.
- **Payment mode**: Trust in the **named relay** to:
  - Not collude with senders to release keys without payment
  - Not leak wrapped content keys to unauthorized parties
  - Accurately verify Bitcoin confirmations
  A sender MUST choose a relay they or their recipient trusts. Future versions may replace the relay with discrete-log contract (DLC) oracles or BIP-118 covenants for fully trustless payment-mode.

### 7.4 Forward secrecy

The recipient's `device_sk` is long-lived. Compromise of `device_sk` allows decryption of all past envelopes addressed to that device. To limit blast radius, recipients SHOULD rotate device keys on a schedule (reference: every 90 days).

OC Lock v2 intentionally does **not** implement full double-ratchet forward secrecy (Signal Protocol) because:

1. Most real-world flows are sender-to-receiver file drops, not live messaging.
2. The overhead of ratchet state sync across devices/sessions conflicts with the "no server" default.
3. Device-key rotation provides coarse-grained forward secrecy sufficient for the target use cases.

Users with strict FS requirements should use Signal.

### 7.5 Envelopes sealed by an agent

A verifier that accepts an envelope sealed by an OC Agent under a `lock:seal` or `lock:chat` delegation MUST take each recipient from the envelope's `recipients[]`, never from the agent action's `scope_exercised` (oc-agent-protocol SPEC §8.3 step 12a). `mime` and the byte limits describe the plaintext, so a recipient checks them against what it decrypts.

## 8. Test vectors

Test vectors are published as JSON files under `packages/core/test/vectors/` in the companion repository. Each vector includes:

- Inputs: `payload`, `sender_sk`, `recipient_sk`, `nonce_ct`, ephemeral randomness
- Intermediates: `shared`, `kek`, `content_key`
- Outputs: canonical envelope bytes, `id`, `sig.value`

Conforming clients MUST produce byte-for-byte identical envelopes when given the same inputs. Canonicalization determinism is a compliance requirement.

## 9. Versioning

`envelope.v` is an integer. Future incompatible changes increment it. Clients MUST reject envelopes whose `v` they do not support. Minor additions (new `alg` values, new fields under `payment`) are handled by unknown-field tolerance: clients MUST preserve unknown fields when relaying but MAY ignore them when decrypting.

## 10. Compliance checklist

A client is OC Lock v2 compliant if and only if:

- [ ] Generates device keys as X25519 and stores `device_sk` non-extractable (when WebCrypto permits)
- [ ] Produces binding statements byte-for-byte per §3.2
- [ ] Publishes kind-30078 records per §3.3 with BIP-322 binding signature
- [ ] Canonicalizes envelopes per §5 and produces identical `id` values across implementations
- [ ] Accepts and produces all required envelope fields per §4.1
- [ ] Verifies sender BIP-322 signatures before accepting envelope contents, with `sig.pubkey` equal to `from.address` (§4.3)
- [ ] Uses a device record only for the address its binding statement signs, under that address's `d` tag (§3.3)
- [ ] Treats a Nostr key as a device's inbox only as §3.4 allows: from 2027-01-21 only a v3 record's signed `nostr_pk`, and still seals to a live v2 bind's `device_pk`; re-binds a v2 device with the v2 statement's `created_at` (§3.4)
- [ ] Seals only to live binds: applies every revocation whose BIP-322 signature verifies, from any relay and any Nostr key, whatever its tags, by signed timestamps, retiring every bind of the device for one that signs no readable `revoked_at`, and treats a bind dated ahead of its clock as not live yet (§3.5)
- [ ] Dates a revocation it signs no earlier than its clock and the latest `created_at` among that device's binds (§3.5)
- [ ] Files a revocation it publishes under the §3.3 `d` tag: a self-revocation under the device's own key, a revocation of another device under a fresh key, never under a key that carries another live bind of the address (§3.5)
- [ ] Enforces `expires_at` when present
- [ ] Emits error codes per §6
