# OC Lock Protocol v2.0 — Specification

**Status:** Stable
**Date:** 2026-04
**Supersedes:** LOCK Protocol v1.0 (adaptor signature) and v1.1 (Proof-of-Access)

---

## 0. Notation

- All bytes serialized as lowercase hex unless marked `base64url`.
- `||` denotes byte concatenation.
- `KDF()` = HKDF-SHA256 per RFC 5869.
- `AEAD()` = AES-256-GCM per NIST SP 800-38D (12-byte IV, 16-byte tag).
- `ECDH(k, P)` = standard X25519 function per RFC 7748. Output is 32 bytes.
- `BIP322(addr, msg)` = BIP-322 signature of `msg` by `addr`, encoded as base64.
- Canonical JSON = UTF-8 encoded JSON with lexicographically sorted object keys, no insignificant whitespace, LF-terminated. See §7.

## 1. Actors

- **Sender** — the party creating a vault.
- **Recipient** — the party able to unseal the vault.
- **Device** — a browser or app instance holding a device keypair bound to a Bitcoin identity.
- **Directory** — a Nostr relay (or set of relays) that stores device-key records.
- **Relay (optional)** — a server that holds payment-gated content keys and releases them upon observing a qualifying Bitcoin payment.

A sender and recipient may be the same person (vault-for-self, password manager pattern).

## 2. Identities

An **OC identity** is the pair `(btc_address, attestation_id)` where:

- `btc_address` is a mainnet Bitcoin address (P2WPKH, P2TR, or P2PKH)
- `attestation_id` is the SHA-256 of a canonical OrangeCheck message signed by that address per the [OrangeCheck SPEC §3](https://ochk.io/docs/spec)

A recipient MUST have an OC identity known to the sender. OC Lock does not publish recipient pubkeys; it publishes **device keys** (§3) addressable by the recipient's Bitcoin address.

## 3. Device keys

A **device key** is a long-lived X25519 keypair generated by a recipient in a particular client/device and bound to their Bitcoin identity by a BIP-322 signature.

### 3.1 Generation

```
(device_sk, device_pk) := x25519_keygen()      // 32-byte each
```

`device_sk` MUST be stored in a confidential local store (IndexedDB with `extractable=false` via WebCrypto if available, else plaintext). `device_sk` MUST NOT leave the device.

### 3.2 Binding

The recipient signs the **binding statement** with their Bitcoin address:

```
binding_statement := "oc-lock:device-bind:v2\n"
                  || "address: "        || btc_address    || "\n"
                  || "device_pk: "      || hex(device_pk) || "\n"
                  || "device_id: "      || device_id      || "\n"    // random 16-byte hex
                  || "created_at: "     || iso8601_utc    || "\n"
```

`binding_sig := BIP322(btc_address, binding_statement)`.

### 3.3 Publication

The **device record** is published to Nostr as an addressable event of kind `30078`:

```
event.kind    = 30078
event.tags    = [
  ["d",           "oc-lock:device:" || btc_address],
  ["addr",        btc_address],
  ["device_id",   device_id],
  ["device_pk",   hex(device_pk)],
  ["alg",         "x25519"],
  ["binding_sig", base64(binding_sig)]
]
event.content = binding_statement   // exact bytes, including LFs
event.pubkey  = ephemeral_nostr_pubkey   // see §3.4
event.created_at = unix_seconds
```

Clients SHOULD publish to at least three relays from a diverse set. The reference app uses `relay.damus.io`, `relay.nostr.band`, `nos.lol`, `relay.snort.social`.

### 3.4 Nostr authorship

The Nostr event `pubkey` is not tied to the user's Bitcoin identity — any ephemeral Nostr key works, because the authenticity proof is the BIP-322 `binding_sig` verifiable against `btc_address`. A fresh ephemeral Nostr keypair SHOULD be derived deterministically from the device:

```
nostr_sk := hkdf(ikm=device_sk, salt="oc-lock/v2/nostr-key", info="nostr-sk", L=32)
```

This avoids asking wallets to hold Nostr keys.

### 3.5 Rotation and revocation

To rotate, a recipient generates a new `(device_sk, device_pk)` with a new `device_id`, re-signs the binding statement, and publishes a new kind-30078 event. Because kind 30078 is **addressable**, the new event with the same `d` tag replaces the previous record at conforming relays.

To revoke without replacement, the recipient publishes an event with `device_pk` set to `"revoked"` and a fresh `binding_sig` over a revocation statement. Conforming senders MUST refuse to encrypt to a revoked device record.

### 3.6 Multi-device

A recipient with multiple devices MAY publish one record per device by using distinct `d` tags: `oc-lock:device:<addr>:<device_id>`. Senders fetching multi-device records MUST encrypt once per active device (§4.2, `recipients[]`).

## 4. Envelope format

A sealed vault is a single canonical JSON object called the **envelope**. It is referred to by file extension `.lock` and MIME type `application/vnd.oc-lock+json`.

### 4.1 Envelope schema

```json
{
  "v": 2,
  "kind": "identity" | "payment",
  "id": "<32-byte hex envelope id, SHA-256 of canonical envelope without this field and without sig>",
  "alg": { "kem": "x25519", "aead": "aes-256-gcm", "kdf": "hkdf-sha256" },
  "from": {
    "address": "<btc address of sender>",
    "attestation_id": "<sha256 of sender's OC canonical message, optional>"
  },
  "recipients": [
    {
      "address": "<btc address of recipient>",
      "device_id": "<recipient device id>",
      "device_pk": "<32-byte hex X25519 pubkey>",
      "eph_pk": "<32-byte hex X25519 ephemeral pubkey produced for this recipient>",
      "wrapped_key": "<base64url(aead(content_key, kek, nonce_kek))>",
      "nonce_kek": "<12-byte hex>"
    }
  ],
  "ciphertext": "<base64url(aead(payload, content_key, nonce_ct))>",
  "nonce_ct":   "<12-byte hex>",
  "hint":       "<optional plaintext hint, UTF-8, <= 200 bytes, leaking only what sender chooses>",
  "created_at": "<iso8601 utc>",
  "expires_at": "<iso8601 utc | null>",
  "payment": null | {
    "amount_sats": <positive integer>,
    "address":     "<btc address that must be paid>",
    "confirmations": <non-negative integer, default 1>,
    "relay":       "<https url of OC Lock relay>"
  },
  "sig": {
    "alg":     "bip322",
    "pubkey":  "<sender btc address>",
    "value":   "<base64(BIP322(sender_addr, id))>"
  }
}
```

### 4.2 Encryption procedure (identity mode)

Given a `payload` (bytes) and one or more recipient device records:

1. Generate random `content_key` (32 bytes).
2. Generate random `nonce_ct` (12 bytes).
3. Compute `ciphertext = AES-256-GCM(content_key, nonce_ct, payload, aad=envelope_id_draft)` where `envelope_id_draft` is the SHA-256 of the canonical envelope up to and excluding `ciphertext`, `sig`, and `recipients[*].wrapped_key` fields.
4. For each recipient device:
   a. Generate an ephemeral X25519 keypair `(eph_sk, eph_pk)`.
   b. `shared = X25519(eph_sk, device_pk)` (32 bytes).
   c. `kek = HKDF-SHA256(ikm=shared, salt=nonce_ct, info="oc-lock/v2/kek:" || device_id, L=32)`.
   d. Generate `nonce_kek` (12 bytes).
   e. `wrapped_key = AES-256-GCM(kek, nonce_kek, content_key, aad=device_id)`.
   f. Zeroize `eph_sk`.
5. Compute final canonical envelope; set `id = sha256(canonical_bytes_without_sig)`.
6. `sig.value = BIP322(sender_addr, id)`.
7. Zeroize `content_key`.

### 4.3 Decryption procedure (identity mode)

Given an envelope and a local `(device_id, device_sk)` pair:

1. Recompute `id` from the envelope and compare to `envelope.id`. Reject on mismatch.
2. Verify `sig.value` against `id` using BIP-322 and `sig.pubkey`. Reject on failure. (Clients MAY skip sender verification for sender == self.)
3. Find a recipient entry matching your local `device_id`. If none, this vault is not for you — reject.
4. `shared = X25519(device_sk, eph_pk)`.
5. `kek = HKDF-SHA256(ikm=shared, salt=nonce_ct, info="oc-lock/v2/kek:" || device_id, L=32)`.
6. `content_key = AES-256-GCM.decrypt(kek, nonce_kek, wrapped_key, aad=device_id)`. Reject on tag failure.
7. `payload = AES-256-GCM.decrypt(content_key, nonce_ct, ciphertext, aad=envelope_id_draft)`. Reject on tag failure.
8. Zeroize `shared`, `kek`, `content_key`.

### 4.4 Payment mode

Payment mode replaces step 4 in §4.2 with a single "recipient" that is the **relay**:

```json
"recipients": [
  {
    "address": "<relay identity>",
    "device_id": "oc-lock-relay",
    "device_pk": "<relay X25519 pubkey>",
    "eph_pk": "...",
    "wrapped_key": "...",
    "nonce_kek": "..."
  }
],
"payment": {
  "amount_sats": 10000,
  "address":     "bc1q...",
  "confirmations": 1,
  "relay":       "https://oc-lock.example/relay"
}
```

The relay holds the content key wrapped for its own device key. A recipient unsealing a payment-mode vault performs:

1. Authenticate to the relay using OC sign-in (OrangeCheck challenge-response over the recipient's Bitcoin address).
2. Request release: `POST /release { envelope_id, unlock_address, tx_proof }` where `tx_proof` identifies a confirmed Bitcoin transaction paying `payment.amount_sats` to `payment.address` with at least `payment.confirmations` confirmations.
3. Relay verifies via a Bitcoin block explorer that the tx exists, has the required amount and confirmations, and is spent from `unlock_address` (if vault requires address binding).
4. Relay unwraps `content_key` using its own `device_sk`, re-wraps it for the recipient's **authenticated** device (fetched from Nostr), and returns the new `recipients[]` entry.
5. Recipient decrypts normally via §4.3.

The relay is a trust anchor. Clients MUST display the relay URL and identity prominently before accepting payment-mode vaults. Anyone may run a relay; the reference implementation is permissionless and stateless between a funded release request and its response.

## 5. Canonicalization

The canonical byte representation of an envelope is required for computing `id` and for BIP-322 signing. Canonical form:

- UTF-8 JSON with keys sorted lexicographically at every level.
- No insignificant whitespace (no spaces after `:` or `,`, no leading/trailing whitespace).
- Arrays preserve order. Within `recipients[]`, entries MUST be sorted by `device_id` ascending.
- Numbers serialized with no fractional zeros and no exponents for integers within IEEE 754 double range.
- Strings serialized with `\uXXXX` escapes only for control characters and `"` / `\`; all other codepoints literal.
- Final byte is LF (`0x0a`).

Reference: [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785), with the additional requirement on `recipients[]` ordering.

`envelope_id_draft` used as AAD in step 4.2.3 and 4.3.7 is computed from the envelope with `ciphertext=""`, `sig={}`, and each `recipients[*].wrapped_key=""`, then canonicalized.

## 6. Errors

Client errors MUST use these codes. Users see short human-readable messages; logs see the code.

| Code | Meaning |
|---|---|
| `E_NO_DEVICE` | No device key found for this browser. Recipient must register. |
| `E_NOT_ADDRESSED` | Envelope does not include the recipient's `device_id`. |
| `E_BAD_SIG` | Sender BIP-322 signature did not verify. |
| `E_BAD_TAG` | AEAD authentication failed (tampered envelope or wrong key). |
| `E_EXPIRED` | `expires_at` is in the past. |
| `E_REVOKED` | Recipient device record is revoked on Nostr. |
| `E_PAYMENT_UNMET` | Relay could not verify required payment. |
| `E_RELAY_UNREACHABLE` | Relay did not respond. |

## 7. Security model

### 7.1 What OC Lock proves

- **Authenticity**: The envelope was signed by the holder of `from.address` at a specific moment (BIP-322 over `id`).
- **Confidentiality**: Only holders of a `device_sk` listed in `recipients[]` can derive `content_key`.
- **Identity binding**: A recipient's `device_pk` is bound to their `btc_address` by a BIP-322 signature in the Nostr directory record. Senders MUST verify the binding before encrypting.

### 7.2 What OC Lock does NOT prove

- **Order / freshness**: Envelopes include `created_at` but are not ordered. Use OrangeCheck challenge-response for freshness-critical flows.
- **Delivery**: The protocol does not ship vaults. Use any transport (URL, email, Nostr, dead drop).
- **Metadata privacy**: `from.address`, `recipients[*].address`, `hint`, and `payment.address` are plaintext. A sender who wants metadata privacy MUST redact these and rely on out-of-band addressing.

### 7.3 Trust assumptions

- **Identity mode**: No trust in any third party. Nostr relays may censor but cannot forge: the BIP-322 binding signature is verifiable offline.
- **Payment mode**: Trust in the **named relay** to:
  - Not collude with senders to release keys without payment
  - Not leak wrapped content keys to unauthorized parties
  - Accurately verify Bitcoin confirmations
  A sender MUST choose a relay they or their recipient trusts. Future versions may replace the relay with discrete-log contract (DLC) oracles or BIP-118 covenants for fully trustless payment-mode.

### 7.4 Forward secrecy

The recipient's `device_sk` is long-lived. Compromise of `device_sk` allows decryption of all past envelopes addressed to that device. To limit blast radius, recipients SHOULD rotate device keys on a schedule (reference: every 90 days).

OC Lock v2 intentionally does **not** implement full double-ratchet forward secrecy (Signal Protocol) because:

1. Most real-world flows are sender-to-receiver file drops, not live messaging.
2. The overhead of ratchet state sync across devices/sessions conflicts with the "no server" default.
3. Device-key rotation provides coarse-grained forward secrecy sufficient for the target use cases.

Users with strict FS requirements should use Signal.

## 8. Test vectors

Test vectors are published as JSON files under `packages/core/test/vectors/` in the companion repository. Each vector includes:

- Inputs: `payload`, `sender_sk`, `recipient_sk`, `nonce_ct`, ephemeral randomness
- Intermediates: `shared`, `kek`, `content_key`
- Outputs: canonical envelope bytes, `id`, `sig.value`

Conforming clients MUST produce byte-for-byte identical envelopes when given the same inputs. Canonicalization determinism is a compliance requirement.

## 9. Versioning

`envelope.v` is an integer. Future incompatible changes increment it. Clients MUST reject envelopes whose `v` they do not support. Minor additions (new `alg` values, new fields under `payment`) are handled by unknown-field tolerance: clients MUST preserve unknown fields when relaying but MAY ignore them when decrypting.

## 10. Compliance checklist

A client is OC Lock v2 compliant if and only if:

- [ ] Generates device keys as X25519 and stores `device_sk` non-extractable (when WebCrypto permits)
- [ ] Produces binding statements byte-for-byte per §3.2
- [ ] Publishes kind-30078 records per §3.3 with BIP-322 binding signature
- [ ] Canonicalizes envelopes per §5 and produces identical `id` values across implementations
- [ ] Accepts and produces all required envelope fields per §4.1
- [ ] Verifies sender BIP-322 signatures before accepting envelope contents
- [ ] Refuses encryption to revoked device records
- [ ] Enforces `expires_at` when present
- [ ] Emits error codes per §6

## 11. IANA / external identifiers

- Nostr event kind: **30078** (addressable, general replaceable range). The `d` tag namespace `oc-lock:device:*` is claimed by this spec.
- File extension: `.lock`
- MIME type: `application/vnd.oc-lock+json` (self-allocated; not IANA-registered as of this writing).
